# HO007：quantlib 量化工具库工程集成

> 依据链：RS017 补课发现生产选品层判据非标准化（内联实现不可复用）→ RS019
> 深度研究确认方向判定/回调触发需重构 → 用户定调"先把形态和信号的量化工具库
> 做好" → goal-d9a2a590 工具库建成（5 模块 ~25 函数，29/34 单测通过）→
> 研究侧确认可用 → 用户指令"走管线去做工程集成"。

## 交付价值评估（治理必备）

| 维度 | 内容 |
|---|---|
| 预期收益 | ① 选品层判据标准化：生产代码从内联实现切换为经过测试的工具库函数——消除索引漂移/参数不一致等隐患；② 新选品策略组装成本从"写新脚本"降为"拼装工具库函数"；③ 后续优化（臂4/衰竭/信号K重构）基于统一基础，多方案可对照切换 |
| 工程成本 | **中低**：代码移植 + import 路径调整 + 依赖（无第三方新依赖）；不影响现有 vnpy_patiming 引擎（detectors.py 零改动）；selection-runner 需验证 poolscan 函数替换后行为一致 |
| 不交付的代价 | 选品/择时判据继续内联（不可测试/不可复用/不可对照），每次策略修改都有索引偏移风险（本会话实证 3+ 次索引 bug） |
| 替代方案 | 维持内联（现状），每次策略修改靠人工核对索引——不可持续 |
| 下行风险 | 有界——quantlib 纯函数替代 poolscan 内联逻辑，替换前后用同一数据集回归断言 |
| **建议** | **交付**——随 HO005/HO006 同批部署，一次集成到位 |

## A. 集成内容

### A1. 代码移植
- `strategy_research/code/quantlib/` → `/opt/aiprj/quantlib/`
  （structure.py / gap.py / pullback.py / entry_signal.py / exhaustion.py / visual.py / __init__.py）

### A2. poolscan.py 切换（工程侧执行）
- `refresh_subscriptions` 中的主力解析（`_pick_by_akshare_oi` / `_pick_by_minute_oi`）不变
- 选品判据（zigzag/趋势判定/支撑压力）从内联改为 `quantlib.structure` 函数调用
- 回调质量判定从内联改为 `quantlib.pullback` 函数调用
- 信号K判定从内联改为 `quantlib.entry_signal` 函数调用
- **行为一致性保证**：替换前后用同一 5m 数据集做回归断言（同一输入→同一输出）
- **分工**：研究侧交付 quantlib 代码+集成规格+回归测试集；工程侧在 production 代码中实施

### A3. selection_runner.py 集成（工程侧执行）
- 选品扫描逻辑引用 quantlib 标准函数
- 入选跟踪 JSONL 写入（HO006-A2）
- **研究侧不直接修改任何生产代码**

## B. 集成后验证

- **B1 回归断言**：替换前后同一输入的函数输出逐值比对（不应有差异）
- **B2 通知 payload**：选品通知内容/格式/频率不应变化
- **B3 换月预警**：HO005 换月预警链路不受影响
- **B4 性能**：扫描节点处理耗时不应显著增加（quantlib 纯函数 vs 内联实现，性能应等同或更优）

## C. 明确不做（边界）

- **研究侧不直接修改任何生产代码**（poolscan.py/selection_runner.py/vnpy_patiming 均为工程侧代码，研究侧只读）
- 不改 vnpy_patiming 引擎（detectors.py / engine.py 零改动）
- 不改已有策略参数（theta/min_leg/er 等全部不变）
- 不新增选品策略（RS019 臂4 hybrid 深化另行立项）
- 不改通知推送通道
