# 清理与版本管理制度（研究范围）

> 依据：用户指令 2026-10-15"阶段性清理自己负责范围的代码文档，做好版本管理"。
> 范围：strategy_research/（研究侧唯一责任范围）；仓库其余部分归开发工程。

## 1. 阶段性清理制度

**节奏**：随里程碑执行（RESEARCH_ROADMAP M1-M6）+ 每月一次例行；重大产出
落档后可加开专项清理。

**范围与动作**（每轮逐项过）：

| 对象 | 动作 | 规则 |
|---|---|---|
| 缓存/临时物（__pycache__/.pytest_cache 等） | 直接删除 | 可再生，git 已忽略（*.pyc） |
| 终局一次性诊断脚本 | 移入 `code/analysis/_archive/`（移动优于删除） | 前提：报告引用关系核查+头部标注 ARCHIVED；活动脚本不动 |
| 过期文档状态 | 状态栏更新（draft→final→superseded），不删原文 | 勘误保留原文（先例：v1_acceptance 勘误） |
| 重复/冲突内容 | 合并进权威文档，旧文标注"已并入 XXX" | 权威文档=三治理文件+各 RS |
| 产出物（assets） | 只增不删；中间产物标注 FINAL/CHECK 状态 | 有档案引用的文件一律保留 |
| 根目录 | 只放治理级文档；新类别先立约定再建文件 | 00_conventions §0 联保约定 |

**红线**：先刷新后清理（重读当前状态）；任何文件删除前必须核查档案引用；
清理轮次记录入本文件 §3 台账。

## 2. 版本管理制度

- **职责边界（用户裁决 2026-10-15：授权研究侧自主提交）**：研究侧获授权对
  `strategy_research/` 路径做**阶段性 git commit**——约束：①路径限定
  strategy_research/，不碰仓库其余任何路径；②先刷新后提交（git status 核对
  +pytest 全绿才提）；③只 commit 不 push（push/远端同步归工程节奏）；
  ④merge/rebase/历史改写仍归开发工程。
- **研究侧职责（本制度）**：
  1. **变更可追溯**：三治理文件（HANDOFF/STATUS/STRATEGY_TABLE）每会话同步
     （已有纪律）+ 本文件 §3 清理台账 + 各文档维护记录——保证任何时点可从
     文档链重建"什么时间改了什么"；
  2. **阶段性归档点**：每里程碑（M1-M6）产出《归档清单》（当期新增/修订
     文件清单+要点摘要，§3 附），随 NOTE 带至工程对话批量提交——工程提交
     时即形成版本节点；
  3. **提交前自检**：pytest 全绿（quantlib 50 项+管线 15 项）+ 无缓存文件
     混入 + 状态栏一致，再交工程；
  4. **版本内容规范（供工程提交参考）**：commit message 建议
     `docs(research): <里程碑/主题>` / `feat(research-code): <脚本主题>`，
     研究产出与工程代码分开成 commit。
- **版本管理授权（已裁决）**：研究侧自主 commit 已获用户授权（2026-10-15，
  见 §2 职责边界）——版本节点由研究侧自主形成，工程继续拥有其余范围与
  全部 merge 操作。
